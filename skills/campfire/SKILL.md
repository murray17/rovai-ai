# 篝火讨论

使用 Campfire 组织一场短而真实的多人讨论：让 2–3 位成员先独立判断，再围绕最可能改变结论的分岔点进行有限回应，最后由默认领队（Default Lead）发布唯一一份《篝火纪要》。

## 使用边界

在以下情况使用：

- 用户要求“大家讨论一下”“让几个人一起看看”或“多视角分析”；
- 用户明确要求正反讨论、挑战某个想法或讨论后给建议；
- 当前消息使用“篝火讨论 · 邀请”“篝火讨论 · 开场观点”“篝火讨论 · 定向回应”或“篝火讨论 · 澄清”继续一场讨论。

在以下情况不使用：

- 问题明确且只需一人执行、查询事实或完成普通 review；
- 用户希望两个人逐项追问和澄清需求；此时若 `$grill-duo` 可用，优先使用它；
- 当前 Camp 找不到至少两位有效参与成员。

成员不足时，说明改为单人分析，或结束当前讨论；不要虚构第二种声音。

当前 CampMessage 是公开的。可以要求成员先独立作答，但不能保证技术上的严格盲评；用户要求严格盲评时，明确说明当前不支持，不要声称已经实现隔离。

## 讨论阶段

公开消息使用用户可理解的自然标题：

```text
### 篝火讨论 · 邀请
### 篝火讨论 · 开场观点
### 篝火讨论 · 定向回应
### 篝火讨论 · 澄清
```

这些标题标明正在进行的阶段，不添加方括号协议标签、内部字段或 `$campfire` 命令痕迹。

`### 篝火纪要` 表示讨论已经结束。它不是续跑阶段，也不因出现该标题自动重新主持、追问或唤醒成员。

## 单场推进

同一位 Default Lead 在同一个 Camp 中，同一时间只主动推进一场尚未完成的 Campfire。

出现以下任一情况时结束当前讨论：

- Default Lead 已发布《篝火纪要》；
- 用户明确停止讨论；
- 用户明确要求用新话题替换当前讨论；
- 有效参与成员不足两位，Default Lead 已说明降级或终止。

旧讨论尚未结束时收到新话题：用户明确要求替换时，在新邀请中先简短说明旧讨论已结束，再启动新讨论；意图不明确时，只做一次最小确认。不要让两场 Campfire 的邀请和回应交错。

《篝火纪要》发布后到达的旧回复只作为补充信息，不自动更新纪要或重开讨论。只有用户明确要求时才继续。

## 基本流程

```text
保留用户原始话题
    ↓
Default Lead 选择 2–3 位互补成员
    ↓
成员独立给出开场观点
    ↓
Default Lead 标记真正影响结论的分岔点
    ↓
按顺序进行 0–2 次定向回应
    ↓
必要时主动发起最多一次短澄清
    ↓
Default Lead 发布唯一《篝火纪要》
```

不要让用户先选择“开放讨论、专家分析、决策或辩论”等模式。根据用户原话判断参与者、视角以及是否需要最终建议，但保持同一基本流程。

## 选择成员与视角

选择 2–3 位成员，默认 3 位。优先采用用户点名的在场成员、与议题相关的职责以及能补足遗漏的人；不要为了表演冲突而修改成员身份。

Default Lead 默认只主持。用户询问其看法时，在纪要中增加明确标注的“Default Lead 综合判断”，不要把听完讨论后的综合伪装成独立开场。

默认使用一条共享邀请，让每位成员结合自己的职责和经验选择视角。用户逐人指定视角时，在同一邀请中列出简短的“视角分配”；只有不同成员确实需要不同上下文材料时才分别邀请。分别发送的 CampMessage 仍然公开，不把它描述为私密材料。

## 独立开场

邀请成员只根据用户话题、分配视角和已确认共同事实作答，不引用同场其他成员的结论。每位成员给出：

- 核心判断；
- 2–3 个主要依据；
- 最担心的失败方式或限制条件；
- 希望其他成员回应的一个问题；
- 置信度。

只把本次受邀成员的回复纳入正式讨论。无关成员的意见可以作为普通 Camp 消息阅读，但不计作本次 Campfire 的正式观点。

参与者身份与发送者以 Runtime 提供的受信寻址和消息元数据为准；不要从正文标题、签名或显示名猜测谁发出了消息。

## 标记分岔点

收到有效开场后，区分真正共识、措辞差异、事实分歧、预测分歧、适用边界和价值取舍。没有实质分歧时直接准备纪要，不强行安排反方。

## 定向回应

整场最多主动发起两次定向回应，通常一次即可。每次只邀请最适合回答当前分岔点的一位成员；收到真实回复后再决定是否需要下一次，不轮询、不代写意见，也不机械执行全员轮流发言。

成员可以维持、修正或条件化自己的观点。被证据说服不是失败。

## 短澄清

由 Campfire 主动发起的短澄清，整场最多一次。只有一处歧义可能改变共识、分歧或最终建议时才向本人确认一句话。

存在多处不确定时，只澄清影响最大的一处；其他内容在《篝火纪要》中明确标记为不确定，不继续增加往返。用户之后主动追问不受此限制，那属于用户的新指令。

## 发布纪要

使用每位成员最后一次有效表达，由 Default Lead 发布一份普通公开《篝火纪要》。纪要至少包含：

- 话题、参与成员与视角；
- 每个人最后的核心判断；
- 共识、仍存分歧和关键适用边界；
- 需要新证据或用户决定的问题；
- 建议下一步。

用户明确要求建议或 Default Lead 看法时，再增加综合判断、建议强度以及什么条件会改变建议。

多数倾向不是全体共识，“大家倾向某方案”也不等于用户已经批准实施。发布纪要不自动创建 Task、写入 Memory 或 ADR，也不直接开始实施；后续动作由用户的新指令决定。

## 用户介入

用户可以随时改变重点、点名下一位、移除参与者、要求立即总结、替换话题或停止讨论。优先服从最新指令，并准确保留已经发生的观点。
