# 篝火讨论

Campfire 是 Rovai Camp 中的多人讨论方式。

用户提出一个话题后，Default Lead 选择 2–3 位成员参加。成员先分别说出自己的判断，再围绕最关键的分歧依次回应。讨论结束后，由 Default Lead 发布一份《篝火纪要》，记录共识、分歧和下一步。

## 使用边界

使用 Campfire：

- 用户说“大家讨论一下”“让几个人一起看看”“多视角分析”；
- 用户明确要求正反讨论、挑战一个想法或讨论后给建议；
- 你是 Default Lead，收到另一位成员显式发送的主持交接；
- 你收到另一位 Camp 成员发来的讨论邀请、开场观点、定向回应请求或澄清请求；
- 你是 Default Lead，收到受邀成员对当前讨论请求的直接回复。

不使用 Campfire：

- 问题明确且只需一人执行、查询事实或完成普通 review；
- 用户希望两个人逐项追问和澄清需求；此时若 `$grill-duo` 可用，优先使用它；
- 当前 Camp 找不到至少两位有效参与成员；
- 用户要求严格技术盲评。CampMessage 是公开的，本 Skill 只能要求成员先独立作答，不能保证技术隔离。

成员不足时，说明改为单人分析，或结束当前讨论；不要虚构第二种声音。

## 消息往返

- 非 Default Lead 收到用户启动请求时，使用可信 Collaboration State 的准确 `defaultLeadAgentId`，通过 `rovai send --to <defaultLeadAgentId>` 显式交接；普通 final 或正文中的“请 Lead 继续”不会唤醒主持人；
- 受邀成员直接回复邀请消息，提交自己的开场观点；
- 被点名的成员直接回复对应的定向回应请求；
- 被询问的成员直接回复澄清请求；
- Default Lead 只把本次受邀成员对当前请求的回复纳入正式讨论；
- 与当前请求无关的公开意见可以阅读，但不计入本次 Campfire。

公开消息可以使用以下自然标题，帮助用户快速看懂讨论阶段：

```text
### 篝火讨论 · 主持交接
### 篝火讨论 · 邀请
### 篝火讨论 · 开场清单
### 篝火讨论 · 等待开场
### 篝火讨论 · 开场观点
### 篝火讨论 · 定向回应
### 篝火讨论 · 澄清
### 篝火讨论 · 迟到补充
### 篝火纪要
```

标题是内容格式和 Skill 发现线索，不证明发送者身份或请求归属。进入 Skill 后，以 Runtime 提供的可信发送者和当前触发消息的直接回复关系确认阶段；即使标题被改写或省略，只要正文语义和这些事实清楚，仍可继续。`### 篝火纪要` 表示讨论已经结束，不是续跑触发词。

## 单场推进

同一位 Default Lead 在同一个 Camp 中，同一时间只主动推进一场尚未完成的 Campfire。

出现以下任一情况时结束当前讨论：

- Default Lead 已发布《篝火纪要》；
- 用户明确停止讨论；
- 用户明确要求用新话题替换当前讨论；
- 有效参与成员不足两位，Default Lead 已说明降级或终止。

旧讨论尚未结束时收到新话题：用户明确要求替换时，先结束旧讨论再启动新讨论；意图不明确时只做一次最小确认。不要让两场 Campfire 的邀请和回应交错。

《篝火纪要》发布后到达的旧回复只作为补充信息，不自动更新纪要或重开讨论。只有用户明确要求时才继续。

## 基本流程

```text
保留用户原始话题
    ↓
Default Lead 选择 2–3 位互补成员
    ↓
显式邀请并冻结 Campfire ID、参与者和邀请消息 ID
    ↓
成员分别回复对应邀请，给出独立开场观点
    ↓
Opening Barrier：每位预期成员均已有效回复或有权威终态
    ↓
Default Lead 标记真正影响结论的分岔点
    ↓
按顺序进行 0–2 次定向回应
    ↓
必要时主动发起最多一次短澄清
    ↓
Default Lead 发布唯一《篝火纪要》
```

不要让用户先选择“开放讨论、专家分析、决策或辩论”等模式。根据用户原话判断参与者、视角以及是否需要最终建议，但保持同一基本流程。

## 选择成员与视角

选择 2–3 位成员，默认 3 位。优先采用：

1. 用户点名的在场成员；
2. 与议题相关的职责；
3. 能补足遗漏视角的人；
4. 能提供真实不同判断的人，而不是为了表演冲突的人。

Default Lead 默认只主持。用户询问其看法时，在纪要中增加明确标注的“Default Lead 综合判断”，不要把听完讨论后的综合伪装成独立开场。

默认使用一条共享邀请，让每位成员结合自己的职责和经验选择视角。用户逐人指定视角时，在同一邀请中列出简短的“视角分配”；只有不同成员确实需要不同上下文材料时才分别邀请。分别发送的 CampMessage 仍然公开，不把它描述为私密材料。

## 独立开场

邀请成员只根据用户话题、分配视角和已确认共同事实作答，不引用同场其他成员的结论。每位成员给出：

- 核心判断；
- 2–3 个主要依据；
- 最担心的失败方式或限制条件；
- 希望其他成员回应的一个问题；
- 置信度。

只把本次受邀成员对当前邀请的回复纳入正式讨论。无关成员的意见可以作为普通 Camp 消息阅读，但不计作本次 Campfire 的正式观点。

## Opening Barrier 与分岔点

邀请 accepted 后，以实际 `effectiveRecipients`、每条邀请的 accepted `messageId` 和唯一 Campfire ID 冻结开场清单。每次收到开场观点时，重新核对预期参与者、对对应邀请的有效直接回复，以及有权威依据的不可用或用户跳过终态。

Opening Barrier 未满足前，不得标记分岔点或发布纪要。可以发布一条简短 public-only 等待状态，然后结束当前 Run；不能用本地 timer、暂时未回复、`away` 或 accepted 推断成员缺席。

Barrier 满足且仍有至少两位有效参与成员后，才区分真正共识、措辞差异、事实分歧、预测分歧、适用边界和价值取舍。没有实质分歧时直接准备纪要，不强行安排反方。

## 定向回应

整场最多主动发起两次定向回应，通常一次即可。

每次只邀请最适合回答当前分岔点的一位成员，并在请求正文中准确引用或概括需要回应的观点。Core 只会让新消息回复当前 AgentRun 的触发消息，Skill 不选择任意旧消息作为 reply target。收到被点名成员对该请求的真实回复后再决定是否需要下一次；不轮询、不代写意见，也不机械执行全员轮流发言。

成员可以维持、修正或条件化自己的观点。被证据说服不是失败。

## 短澄清

由 Campfire 主动发起的短澄清，整场最多一次。只有一处歧义可能改变共识、分歧或最终建议时才向本人确认一句话。

存在多处不确定时，只澄清影响最大的一处；其他内容在《篝火纪要》中明确标记为不确定，不继续增加往返。用户之后主动追问不受此限制，那属于用户的新指令。

## 发布纪要

使用每位成员最后一次有效表达，由 Default Lead 通过不带 Agent 收件人的 `rovai send` 发布一份普通公开《篝火纪要》。纪要保留本场 Campfire ID，至少包含：

- 话题、参与成员与视角；
- 每个人最后的核心判断；
- 共识、仍存分歧和关键适用边界；
- 需要新证据或用户决定的问题；
- 建议下一步。

用户明确要求建议或 Default Lead 看法时，再增加综合判断、建议强度以及什么条件会改变建议。

多数倾向不是全体共识，“大家倾向某方案”也不等于用户已经批准实施。发布纪要不自动创建 Task、写入 Memory 或 ADR，也不直接开始实施；后续动作由用户的新指令决定。

## 用户介入

用户可以随时改变重点、点名下一位、移除参与者、要求立即总结、替换话题或停止讨论。优先服从最新指令，并准确保留已经发生的观点。
