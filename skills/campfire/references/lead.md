## 1. 进入主持流程

只有以下两类触发可以进入第一轮：

1. 用户直接要求当前 Default Lead 组织多人讨论；
2. 一位普通成员发送的明确《篝火讨论 · 转交请求》，并且转交内容表明用户只触达该成员、明确要求召集多人讨论。

普通成员观点、普通 A2A 消息、成员回传和迟到消息都不能进入启动分支。

开始前确认：

- 用户原始话题；
- 用户是否要求最终建议、比较、决策或正反讨论；
- 用户是否点名成员或指定视角；
- 当前 Camp 中没有另一场由自己推进且尚未结束的 Campfire。

用户明确要求替换当前话题时，先停止旧讨论，再开始新讨论。

## 2. 选择参与成员

选择 2–3 位当前可参与成员，默认 3 位。优先顺序：

1. 用户点名的在场成员；
2. 与议题直接相关的职责和经验；
3. 能补足遗漏视角的成员；
4. 能提供真实不同判断的人，而不是为了表演冲突的人。

使用可信 Collaboration State 中的 canonical Agent ID 寻址，不根据显示名猜测路由身份。

Default Lead 默认只主持。用户明确询问主持人的看法或要求最终建议时，在纪要中增加“Default Lead 综合判断”，不要在第一轮先给出倾向。

有效参与成员不足两位时，说明降级为单人分析或结束，不创建 Gather。

## 3. 第一轮：独立观点 Gather

运行：

```text
rovai gather --help
```

使用一条共享请求，通过重复的 `--to <Agent ID>` 邀请全部成员：

```text
rovai gather --to <agent-a-id> --to <agent-b-id> --to <agent-c-id> --body <第一轮请求正文>
```

请求正文采用以下结构。参与者列表使用普通显示名，不额外使用 `@` 寻址。

```markdown
### 篝火讨论 · 独立观点请求

#### 话题

> <尽量保留用户原话>

#### 已确认的共同事实

- <没有则写“暂无”>

#### 参与成员与视角

- <成员 A>：<视角>
- <成员 B>：<视角>
- <成员 C>：<视角>

#### 本轮任务

请独立给出：

1. 核心判断；
2. 两项主要依据；
3. 一项最重要的风险或限制；
4. 改变判断的条件；
5. 置信度。

#### 回复要求

- 整条正文目标为 200–250 个中文字符，最多不超过 300 个中文字符；
- 只保留上述五项，不重复题目、背景或其他成员观点；
- 只根据本轮话题、共同事实和分配视角独立判断；
- 不发送进度消息；
- 完成后只提交一条完整结果；
- 通过 `rovai send` 返回本请求发送者；
- 不邀请其他成员，不总结全场，不发起下一轮。
```

不要附带主持人的推荐。

只有 `rovai gather` 返回 accepted 时，才视为第一轮已经建立。accepted 后立即结束当前 Run：

- 不再发送普通邀请；
- 不发布参与清单或等待状态；
- 不轮询 Camp；
- 不重复调用 Gather。

## 4. 读取 Gather Completion

当前输入必须是自己发起的请求对应的 `gather_completed`。直接使用 Completion Input 中的：

- 原始请求；
- 参与成员；
- 每个成员的终态；
- 当前有效回传或最终总结兜底；
- 错误或取消信息。

不要从零散公屏消息重建参与者集合。

若 Completion Input 明确以 `bodyTruncated=true` 标记某份结果被截断，不得把缺失内容当作已知。只按当前可见内容使用该结果；无法确认核心结论时，将其标记为不完整观点。不要在 Campfire 中增加 `camp read` 补读流程。

## 5. 处理第一轮结果

当前输入必须是自己发起的独立观点请求对应的 `gather_completed`。

### 判断有效观点

一份结果只有在内容完整、直接回答本轮任务时，才算有效观点。

- 成员成功且结果完整：计入正式观点；
- 成员失败或取消，但保留了一份语义完整的正式结果：可以计入，并在纪要中标记运行状态；
- 只有进度、确认、空泛文本、错误信息或无法确认核心结论的截断结果：不计入正式观点；
- 不替未完成成员补写立场。

### 有效观点数量

- 至少两份：继续判断共识与分歧；
- 只有一份：发布部分纪要，明确未形成有效多人讨论；
- 没有有效观点：发布简短终止说明。

### 判断是否进入回应轮

区分：

- 真正共识；
- 措辞不同但结论一致；
- 事实分歧；
- 预测分歧；
- 适用边界不同；
- 价值取舍不同。

只有存在一个会显著改变最终判断、建议或适用条件的关键分歧时，才进入第二轮。

没有实质分歧时，读取 `notes.md`，直接发布《篝火纪要》。不要为了展示讨论强行安排反方。

## 6. 主持权变化

Gather completion 始终由原发起者处理。

处理第一轮 completion 时，重新检查当前 Collaboration State：

- 若 `selfIsDefaultLead=true`，可以根据分歧情况发起可选的定向回应 Gather；
- 若 `selfIsDefaultLead=false`，继续综合已经收齐的成员观点并直接发布《篝火纪要》，不再发起第二轮 Gather。

处理第二轮 completion 时，无论主持权是否变化，都由原发起者继续综合并发布《篝火纪要》。主持权变化不会丢弃本场已经形成的观点，也不会自动把当前 Campfire 转交给新的 Default Lead。

## 7. 第二轮：定向回应 Gather

整场最多发起一次回应轮，通常邀请分歧最直接的两位成员；只有问题只需要一方补充时才邀请一位。

第二轮请求写入：

- 用户原始话题；
- 第一轮每位有效参与者的“核心立场 + 最主要依据”摘要；
- 唯一的关键分歧；
- 对本轮每位成员的具体回应任务；
- 明确要求提交最终更新立场。

不要复制每位成员的完整第一轮档案。

```markdown
### 篝火讨论 · 定向回应请求

#### 原始话题

> <用户原始话题>

#### 第一轮立场摘要

- <成员 A>：<核心立场 + 最主要依据>
- <成员 B>：<核心立场 + 最主要依据>
- <成员 C>：<核心立场 + 最主要依据，或“未形成完整观点”>

#### 本轮关键分歧

> <只写一个真正影响结论的问题>

#### 定向任务

- <成员 A>：回应 <具体观点、证据或问题>
- <成员 B>：回应 <具体观点、证据或问题>

请分别给出：

1. 更新后的核心判断，并说明维持、修正或条件化；
2. 两项主要依据；
3. 一项最重要的风险或限制；
4. 改变判断的条件；
5. 置信度。

#### 回复要求

- 整条正文目标为 200–250 个中文字符，最多不超过 300 个中文字符；
- 只保留上述五项，不重复题目、背景或其他成员观点；
- 只回应本轮唯一关键分歧；
- 只提交一条完整回应，不发送进度消息；
- 不邀请其他成员，不开启新的讨论轮。
```

通过一次 `rovai gather` 发出。accepted 后立即结束当前 Run，不再发送其他请求或等待状态。

## 8. 处理第二轮结果

当前输入必须是自己发起的定向回应请求对应的 `gather_completed`。

结合当前可见的公屏第一轮观点、第二轮回应和主持人的当前会话上下文生成最终纪要：

- 有完整回应的成员，以回应后的立场为最终立场；
- 回应失败、截断或内容不完整的成员，继续使用当前上下文中可确认的第一轮立场，并标记“未完成定向回应”；
- 未进入第二轮的成员，继续使用第一轮立场；
- 明确修正的观点按修正后版本记录；
- 条件性支持不能写成无条件共识；
- 当前上下文无法确认的内容必须标记为未知，不补写。

第二轮完成后必须读取 `notes.md` 并发布《篝火纪要》：

- 不创建第三个 Gather；
- 不再发起独立澄清；
- 不要求其他成员继续回应。

## 9. 转交请求

普通成员只在用户单独触达该成员并明确要求召集多人讨论时，才能发送：

```markdown
### 篝火讨论 · 转交请求

#### 用户话题

> <逐字保留用户原始话题>

#### 用户指定成员

- <没有则写“未指定”>

#### 期望输出

<讨论、比较、建议或决策>
```

收到转交后，核对当前没有未结束的 Campfire，再按正常第一轮流程处理。

除这种明确转交外，任何 Agent 消息都不能启动新 Campfire。

## 10. 用户介入

用户可以随时：

- 停止讨论；
- 替换话题；
- 移除参与者；
- 要求立即总结；
- 指定是否需要最终建议。

优先服从用户最新指令。用户要求立即总结时，使用已经形成的有效观点发布部分纪要，准确标记未完成成员，不继续创建 Gather。

用户停止或替换话题后，旧 Gather 的迟到结果不自动恢复旧讨论。
