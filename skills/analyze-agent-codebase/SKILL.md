# Agent 代码库分析

从入口、调用链、状态变化和持久化边界还原系统实际如何运行。把 README 和设计文档视为待核对的设计主张，不把关键词命中、类名或目录名当作架构结论。

## 不变量

- 先遵守目标仓库的 `AGENTS.md`、`CLAUDE.md`、文档路由和只读边界。
- 分析请求默认只读。只有用户明确要求生成或维护文档时，才写入分析产物；不得顺手修改实现。
- 以可执行源码、配置装配、schema/migration 和测试为实现证据；用文档解释意图并检查代码—文档漂移。
- 每个重要结论标为 `已确认`、`推断` 或 `未知`。推断必须写出推理链，未知不得用常见框架行为补齐。
- 重要结论至少引用一个源码位置和相关 symbol；跨模块行为给出入口到副作用的调用链。
- 不因出现 `agent`、`memory`、`plan`、`tool` 或 `middleware` 等名称就认定对应能力存在。
- 使用用户要求的语言；未指定时沿用用户输入语言。

## 选择交付形态

先判断用户要的是哪一种结果：

1. **会话内报告**：用户只要求分析、解释或比较时，在会话中交付，不创建文件。
2. **专题文档集**：用户明确要求沉淀文档、分专题输出或建立阅读顺序时，读取
   [专题文档合同](references/dossier-structure.md)，在仓库文档规则允许的独立目录中创建文档集。
3. **定向问题**：用户只问一个机制时，只追踪覆盖该问题的纵向切片，不机械生成完整架构审计。

如果仓库已有同类分析，先检查其范围、依据和时效；更新正确归宿，避免再建平行 README 或重复总览。

## 工作流

### 1. 冻结范围与现场

- 定位仓库根目录、当前 commit/branch、工作树状态、主要语言、构建入口和生成代码目录。
- 记录用户特别关心的问题、明确排除项和所需交付物。
- 区分源码、测试、生成物、vendor、fixture、示例与历史文档；不要把 fixture 当生产路径。
- 对只读任务记录开始时的工作树状态，结束前复核没有产生改动。

### 2. 建立运行时骨架

从真实入口向内追踪，而不是从名词搜索开始：

```text
CLI / Desktop / API / daemon entry
  → configuration and dependency assembly
  → agent or workflow factory
  → execution / scheduling loop
  → tool, model, delegation and persistence effects
  → events, receipts, recovery and presentation
```

先找 manifest、workspace 配置、binary/package entrypoint、路由注册、依赖装配和核心状态类型。对动态注册系统，继续追踪 registry、plugin loader、decorator/macro 展开点或配置解析器，直到能解释运行时如何获得具体实现。

### 3. 追踪纵向切片

为每个问题选择一个真实触发场景，沿调用链追到可观察副作用和恢复路径。优先覆盖用户点名的轴；完整分析时从以下轴中选择实际存在者：

- Agent 执行循环与 ReAct、Plan-and-Execute、graph/state-machine 或混合控制流；
- 子 Agent 的创建、寻址、上下文隔离、并发、结果压缩与回传；
- Task/plan/progress 的状态机、所有权、取消、重试和完成判定；
- session、context window、compaction、短期状态与长期 Memory；
- model/provider adapter、默认工具、工具 schema、调用路由、权限与审批；
- Skill/prompt/instruction 的发现、选择、装载及其与工具的边界；
- 数据库、文件、cache、queue、event bus、middleware、hook 与 observability；
- extension seam、错误恢复、幂等、并发控制、安全边界和测试策略。

不要为了凑齐清单而虚构不存在的子系统。详细判据和专题合并规则见
[专题文档合同](references/dossier-structure.md)。

### 4. 建立证据账本

边读边维护紧凑证据表，不在最后凭印象补引用：

| 结论 | 状态 | 代码证据 | 测试/运行证据 | 限制或反证 |
| --- | --- | --- | --- | --- |
| `<可证伪的完整句子>` | 已确认 / 推断 / 未知 | `<path:line + symbol/call chain>` | `<test/fixture/trace>` | `<冲突、动态边界或缺口>` |

引用应支持完整意图。例如“系统支持子 Agent”至少要说明谁创建、如何投递上下文、在哪个隔离边界运行、结果如何回到调用者；只引用一个 `spawn_agent` 字符串不够。

### 5. 形成架构判断

- 把“组件清单”提升为职责、权威来源、数据流和控制流，而不是目录导览。
- 区分同步调用、异步消息、持久任务、进程派生和模型内角色扮演；不要统称为多 Agent。
- 区分工作上下文、会话恢复、长期记忆、检索索引和审计历史；不要统称为 Memory。
- 区分 Tool 的可执行能力、Skill 的操作指导、prompt 的模型输入和 permission 的授权边界。
- 对 ReAct 或 Plan-and-Execute 分类展示实际循环、计划的持久性、重规划触发与终止条件；证据不足时使用“类 ReAct”或“混合”并解释限定。
- 同时记录有意义的反证：未找到的恢复路径、只存在接口没有生产注册、文档宣称但代码未接通的能力。

### 6. 交叉验证

- 用至少一个测试、fixture、schema 或运行路径核对关键调用链；测试只能证明其覆盖的行为。
- 回读相关权威文档，列出一致、漂移和未实现的设计主张。用户明确禁止读取文档时跳过此步并说明限制。
- 检查替代入口、feature flag、平台分支和 adapter 差异，避免把一个实现概括成全系统行为。
- 对关键 symbol 做反向引用搜索，确认它进入生产装配，而非孤立代码。

### 7. 交付

先给结论和系统图景，再给证据与限制。至少包含：

- 分析范围、commit/branch 与主要排除项；
- 运行时拓扑和两到三个关键端到端流程；
- 用户点名机制的结论及证据状态；
- 架构优点、真实约束、代码—文档漂移和高价值未知项；
- 代码位置或专题文档的阅读顺序。

不要大段复制源码或现有文档。引用最小必要片段，并以路径、symbol 和简短解释为主。

## ROVAI 协作

大型仓库存在三个以上相互独立的证据域、且当前 Camp 有合格队员时，可以把**证据收集**拆成有界协作请求。每个请求都要给出问题、允许检查的目录、排除项、证据格式和停止条件。

- 保留一个主分析者负责运行时骨架、跨域调用链和最终分类。
- 不让多个队员分别写互相重叠的最终总览；先收证据，再由主分析者消歧合并。
- `rovai send` 的发送成功只证明消息被接受，不证明对方已经开始或完成；等待期间继续追踪主干，不轮询制造噪音。
- 收到结果后抽查关键路径和 symbol，再纳入结论；无法取得搭档时直接降级为单人分析。

## 完成条件

- 每个高层结论都能回到入口、调用链、状态或持久化证据。
- 已确认、推断、未知和代码—文档漂移彼此分开。
- 完整分析覆盖用户指定轴，并对不适用轴明确说明而非填充模板。
- 文档集具有单一索引和明确阅读顺序，没有重复总览。
- 只读请求结束时工作树与开始状态一致；写文档请求只包含授权的分析产物。
