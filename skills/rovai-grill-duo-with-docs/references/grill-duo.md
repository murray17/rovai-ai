# 双人追问协议

## 会话边界

- 持续追问，直到与用户达成共同理解。
- 沿决策树逐项解决问题，先处理会影响后续问题的上游决定。
- 一次只问一个问题，并等待用户回答后再继续。
- 每题都给出推荐答案；不要只罗列选项。
- 能从代码、文档、当前 Camp 上下文或工具查到的事实，自己查，不问用户。
- 真正需要取舍的决定交给用户。
- 在用户明确确认已经达成共同理解前，不开始实施。

## 固定搭档

会话开始时，从当前 Camp 中选择一位不是自己的、仍在场且可以接收协作请求的队员作为固定搭档。
优先选择与当前问题专业最匹配的队员；事实可以从当前上下文或 Camp 读取工具取得时，不要求用户选人。

整场会话使用同一位搭档。只有用户要求、搭档不可用或问题明显跨入另一专业领域时才更换，并说明原因。

如果当前 Camp 没有合格搭档，明确说明已降级为单人追问，然后继续执行相同的逐题协议。不要虚构第二个观点。

## 每个决策点的协作往返

先整理当前唯一的决策点，再通过 `rovai send` 向固定搭档发出显式公共 A2A 请求。需要确认命令参数时运行
`rovai send --help`；使用 Core 解析的精确队员 ID 寻址，不猜测 ID。

请求正文包含 `[GRILL_DUO_REVIEW]`、用户原始目标、当前决策点、已确认事实和决定、候选选项与约束，
以及当前追问者的精确队员 ID。不要附带自己的推荐，避免锚定。

要求搭档独立返回：

1. 容易理解的问题解释；
2. 各选项的利弊与可逆性；
3. 独立建议；
4. 用户可以直接采用的一句话答案。

要求搭档把结果放在 `[GRILL_DUO_ADVISORY]` 正文中，并使用 `rovai send` 精确回复当前追问者。
搭档不得替用户决定、实施、继续委派或一次提出多个问题。

发送成功只证明公共消息和 Message Delivery 已建立，不证明搭档已经开始或完成。不要 sleep、轮询或伪造
搭档意见；结束当前 Run，让事件驱动 Delivery 继续协作链。

## 收到搭档建议后

收到同一决策点的 `[GRILL_DUO_ADVISORY]` 后，不要再次发送该决策点。

结合搭档意见与自己的判断，向用户给出简明解释、关键取舍与可逆性、明确推荐，以及恰好一个需要用户
回答的问题。意见不一致时诚实说明分歧和依据。

用户回答后记录决定，再进入下一个仍受影响的决策点。不要重新询问已经解决的问题。

## 完成

决策树没有未解决分支时，总结目标、已确认决定、约束和风险，然后只问一次用户是否确认已经达成共同
理解。得到明确确认后结束追问；后续实施仍须遵守当前授权和仓库规则。
