# 双人追问

一个负责问到底，一个负责把选项掰开讲明白。让用户只承担真正的取舍，不承担事实搜索或术语翻译。

## 会话边界

- 持续追问，直到与用户达成共同理解。
- 沿决策树逐项解决问题，先处理会影响后续问题的上游决定。
- 一次只问一个问题，并等待用户回答后再继续。
- 每题都给出推荐答案；不要只罗列选项。
- 能从代码、权威文档、当前 AgentRun 已投递上下文，或 Rovai 内置的 Camp 公共历史读取能力取得的事实，自己查，不问用户。
- 真正需要取舍的决定交给用户。
- 在用户明确确认已经达成共同理解前，不开始实施。

## 固定搭档

会话开始时，从当前 Camp 中选择一位不是自己的、仍在场且可以接收协作请求的队员作为固定搭档。
优先选择与当前问题专业最匹配的队员；事实可以从当前 AgentRun 已投递上下文或 Rovai 内置的 Camp 公共历史读取能力取得时，不要求用户选人。

整场会话使用同一位搭档。只有以下情况才更换，并向用户说明原因：

- 用户明确要求更换；
- 搭档已经不在场或不能接收请求；
- 问题明显进入另一专业领域，原搭档无法提供有效判断。

如果当前 Camp 没有合格搭档，明确说明已降级为单人追问，然后继续执行相同的逐题协议。不要虚构第二个观点。

## 每个决策点的协作往返

先整理当前唯一的决策点，再通过 `rovai send` 向固定搭档发出显式公共 A2A 请求。需要确认命令参数时运行
`rovai send --help`；使用 Core 提供的准确 Agent ID 寻址，不猜测 ID。

请求正文必须包含：

- 标记 `[GRILL_DUO_REVIEW]`；
- 用户的原始目标；
- 当前这一个决策点；
- 已确认事实和此前决定；
- 候选选项、约束和可逆性线索；

不要附带自己的推荐，避免锚定搭档。要求搭档独立完成以下四项：

1. 用容易理解的话解释问题；
2. 说明各选项的利弊与可逆性；
3. 给出独立建议；
4. 给出用户可以直接采用的一句话答案。

同时要求搭档把结果放在 `[GRILL_DUO_ADVISORY]` 正文中，并使用 `rovai send` 准确回复当前追问者，不猜测路由身份。
搭档不得替用户做最终决定、开始实施、继续委派或一次提出多个问题。

`rovai send` 成功只证明公共消息和 Message Delivery 已建立，不证明搭档已经开始或完成。发送后不要
sleep、轮询或伪造搭档意见；结束当前 Run，让事件驱动 Delivery 继续协作链。

## 收到搭档建议后

收到同一决策点的 `[GRILL_DUO_ADVISORY]` 后，不要再次发送该决策点，避免往返循环。

结合搭档意见与自己的判断，向用户输出：

- 一段简明的问题解释；
- 关键取舍与可逆性；
- 明确的推荐答案；
- 恰好一个需要用户回答的问题。

如果自己的推荐与搭档不同，诚实说明分歧和依据，不强行合并成虚假共识。

用户回答后，记录已经确认的决定，再进入下一个仍受影响的决策点。不要重新询问已经解决的问题。

## 完成

当决策树没有未解决分支时，简要总结目标、已确认决定、约束和仍然存在的风险，然后只问一次用户是否
确认已经达成共同理解。得到明确确认后结束追问会话；后续实施仍须遵守当前任务授权和仓库规则。
