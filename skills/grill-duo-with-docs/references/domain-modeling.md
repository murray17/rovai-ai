# 领域建模纪律

在设计过程中主动建立和打磨项目领域模型：质疑术语、构造边界场景，并在结论形成时立即记录。
仅仅读取 `CONTEXT.md` 不算领域建模；本纪律用于改变模型。

## 定位领域上下文

如果仓库根目录存在 `CONTEXT-MAP.md`，先读取它并找到当前主题所属的上下文、该上下文的
`CONTEXT.md` 与 ADR 目录。如果只有根 `CONTEXT.md`，使用单一上下文。两者都不存在时，只在第一个
术语真正解决后延迟创建根 `CONTEXT.md`。

仓库自己的文档导航和维护规则始终优先。

## 会话中执行

### 对照词汇表

用户使用的术语与现有 `CONTEXT.md` 冲突时立即指出，并把“沿用现有含义还是形成新概念”作为当前唯一问题。

### 收紧模糊语言

遇到模糊或重载词时提出精确的规范术语。例如“账户”可能实际指客户、登录身份或计费主体；不要让一个词掩盖多个领域概念。

### 构造具体场景

讨论领域关系时构造能够触碰边界和例外的具体场景，迫使概念范围、所有权与生命周期变得明确。

### 与代码交叉验证

用户描述系统行为时检查当前代码与权威文档。发现矛盾就展示证据，让用户决定改变模型还是实现；不要静默选择一边。

### 即时更新词汇表

术语一旦解决就更新适用的 `CONTEXT.md`，不要积攒到会话末尾。使用
[词汇表格式](context-format.md)。`CONTEXT.md` 只保存领域语言，不是规格、草稿或实现决定仓库。

### 谨慎创建 ADR

只有决定同时满足以下三个条件才创建 ADR：

1. 改变成本高；
2. 缺少上下文时会让未来读者意外；
3. 存在真实取舍并选择了其中一种。

使用仓库规定的 ADR 格式；没有仓库规则时使用[通用 ADR 参考](adr-format.md)。
