# 双人追问与文档

## 先路由角色

- 收到文档版复核邀请：进入固定搭档分支，只读取 [双人追问协议](references/grill-duo.md)，返回独立建议；不要读取领域建模、词汇表或 ADR 参考，也不修改项目文档；
- 用户启动会话、回答上一题，或收到本次固定搭档对当前文档版复核邀请的回复：进入邀请者分支，读取下面四份参考，继续逐项追问和文档职责。

公开消息使用：

```text
### 双人追问与文档 · 复核邀请
### 双人追问与文档 · 搭档建议
```

每个决策点使用一条新的文档版复核邀请。搭档建议直接回复该邀请。普通版“双人追问”的消息不会改变当前文档版会话。

自然标题只是 Skill 发现和阅读线索。进入 Skill 后，以 Runtime 提供的可信发送者和当前触发消息的直接回复关系确认角色；标题被改写或省略但正文语义和这些事实清楚时仍可继续。

邀请者分支读取：

- [双人追问协议](references/grill-duo.md)
- [领域建模纪律](references/domain-modeling.md)
- [词汇表格式](references/context-format.md)
- [ADR 判断与通用格式](references/adr-format.md)

执行完整的文档版双人追问协议，同时主动维护领域模型。

## 文档职责边界

邀请者维护项目文档；固定搭档只提供独立复核建议。复核邀请或搭档建议本身都不授权搭档修改文档，也不授权任何成员开始产品实现。

“共同理解前不开始实施”仍然适用于产品代码、配置、Migration、脚本和其他交付物。用户已经回答并形成稳定含义的领域术语，以及满足当前仓库 ADR 准入规则的架构决定，可以由邀请者在会话中写入项目文档；这是本 Skill 的附加职责。

每次写文档前先读取仓库自己的文档导航、`AGENTS.md` 和相关维护规则。仓库规则拥有文件位置、格式、状态、编号、权威边界和验证命令；随包参考只在仓库没有更具体规则时提供默认做法。

## 邀请者的会话内维护

- 术语一旦由用户回答形成稳定含义，立即更新适用的 `CONTEXT.md`；只记录领域含义，不写实现细节；
- 用户表述与现有词汇冲突时，当场指出并把冲突作为当前唯一决策点；
- 用户描述与代码或权威文档不一致时，展示证据并让用户决定改变模型还是实现；
- 只有决定同时满足高逆转成本、缺少上下文会令人意外、并且存在真实取舍时才创建 ADR；
- 收到固定搭档对当前复核邀请的直接回复后继续本分支，对已经形成的术语和达到准入的 ADR 履行维护职责；
- 文档写入后运行仓库要求的文档校验；失败时只修复相关文档，不借机开始尚未获准的产品实现。

最终共同理解摘要同时列出本次新增或修订的领域术语、ADR，以及仍未记录的开放决定。
