# 双人追问与文档

邀请者负责持续追问和文档维护，一位固定搭档负责独立复核。固定搭档只提供建议，不修改项目文档。

## 角色与轮次关联

- 用户启动会话或回答当前开放轮次：作为邀请者继续。
- 当前 AgentRun 由文档版双人追问复核请求直接触发：作为固定搭档，只处理这条请求。
- 当前输入是固定搭档对本轮有效复核邀请的直接回复：作为邀请者继续。

始终以 Runtime 提供的可信发送者、当前 AgentRun 的触发消息和直接回复关系判断角色；消息标题只帮助阅读。

邀请者只把同时满足以下条件的消息作为本轮正式建议：发送者是当前固定搭档，消息直接回复本轮当前有效邀请，并且内容回答本轮问题。普通版建议、旧轮、已失效邀请或迟到建议只作补充，不能推进、回退或重开会话。

邀请者按需读取：

- [领域建模纪律](references/domain-modeling.md)
- [词汇表格式](references/context-format.md)
- [ADR 判断与通用格式](references/adr-format.md)

固定搭档不读取这些文档规则。

## 基本流程

1. 开始时选择一位合格的固定搭档。
2. 每轮选择前提已经确认、彼此不依赖的 1–4 个问题。
3. 把本轮问题一次发给搭档，不附带自己的推荐。
4. 搭档用一条消息逐题给出建议、理由和风险。
5. 邀请者结合双方判断，用一条消息向用户提出本轮全部问题，每题给出推荐。
6. 用户回答后，只关闭明确回答、取消或已经失效的问题；当前轮仍开放时继续处理该轮。
7. 对用户已经确认的术语和达到准入门槛的架构决定及时维护文档。
8. 当前轮全部关闭后，才整理下一轮问题。
9. 没有重要问题后，请用户确认共同理解。
10. 用户确认前不开始产品实现。

依赖本轮其它答案的问题留到下一轮。能从代码、权威文档、工具、当前 AgentRun 已投递上下文或 Camp 公共历史查明的事实，不问用户。

## 固定搭档

固定搭档必须不是自己、仍在当前 Camp、能够接收协作请求。使用 Runtime 或 Core 提供的可信 Agent ID 寻址，不根据显示名或正文猜测 ID。

优先选择与当前问题最匹配的队员，整场使用同一位搭档。只有用户要求、搭档离场或不能接收请求、或者问题明显进入原搭档无法有效判断的专业领域时才更换，并向用户说明原因。

没有合格搭档时，说明降级为单人追问，并继续相同的分轮、开放轮次和文档规则；不要虚构第二个观点。

## 开放轮次

一轮在其中所有问题被明确回答、取消或失效前保持开放。为本轮问题使用稳定编号 `Q1`–`Q4`。

- 未回答问题保留原编号、原问题和已有搭档建议；不要为内容未变的问题重复请求搭档。
- 开放轮次期间不混入新问题。新发现的问题等当前轮全部关闭后再进入下一轮。
- 用户回答改变某题的问题、选项或约束时，原建议对该题失效；保留编号，只重新复核该题。
- 重新复核后，只接受固定搭档对更新后邀请的直接回复作为该题当前建议；更早版本的建议只作补充。
- 用户只回答部分问题时，只维护已经确认部分的文档；在同一条用户消息中继续列出仍开放的原编号和已有建议。

## 请求搭档复核

邀请者使用：

```text
rovai send --to <固定搭档 Agent ID> --body <复核请求>
```

```markdown
### 双人追问与文档 · 复核邀请

**用户目标**

> ...

**已经确认**

- ...

**本轮问题**

### Q1：<问题>

- 主要选项：...
- 重要约束：...
- 可能影响的文档：<词汇表、ADR 或“无”>

### Q2：<问题>

- 主要选项：...
- 重要约束：...
- 可能影响的文档：...

请逐题给出建议、最主要的理由和需要提醒用户的风险。
只提供复核意见，不修改项目文档。
```

初次复核时，一条邀请覆盖整轮。某题因用户改变问题、选项或约束而失效时，新邀请只包含该题及其更新内容。

只有 `rovai send` 返回 `accepted` 后才结束当前响应并等待搭档建议。`accepted` 只证明消息和 Delivery 已建立，不证明搭档已经开始或完成；不轮询、不代写。

## 搭档返回建议

搭档只处理触发当前 AgentRun 的复核请求，使用 Runtime 提供的可信邀请者 Agent ID 作为唯一收件人，不继续委派、不增加问题，也不修改 `CONTEXT.md`、ADR 或其它项目文件。

```markdown
### 双人追问与文档 · 搭档建议

### Q1

- 建议：...
- 理由：...
- 风险：...

### Q2

- 建议：...
- 理由：...
- 风险：...
```

```text
rovai send --to <邀请者 Agent ID> --body <建议>
```

只有命令返回 `accepted` 后才结束当前响应。不要替用户决定或开始实施。

## 邀请者询问用户

结合双方判断，一次向用户提出本轮全部开放问题。每题说明主要取舍、自己的推荐、搭档看法，以及确认后可能影响的文档；双方意见不同时准确说明分歧。

```text
rovai send --to-user --body <本轮问题>
```

只有命令返回 `accepted` 后才结束当前响应并等待用户。部分回答后的同轮续问只保留仍开放的问题，不改变编号或重复已经关闭的问题。

## 维护文档

- 只记录用户明确确认的术语和决定；未回答、含糊或仅由搭档建议的内容不得写成已确认事实。
- 稳定的领域术语及时写入适用的 `CONTEXT.md`；与现有词汇冲突时先问清楚。
- 只有难以改变、缺少背景会令人意外、且存在真实取舍的决定才记录 ADR。
- 每次写入前读取仓库的文档导航、`AGENTS.md` 和相关维护规则；仓库规则决定文件位置、格式、编号和校验命令。
- 文档校验失败时只修复相关文档，不开始尚未获准的产品实现。

## 完成与恢复

没有重要问题后，总结已确认决定、关键约束和风险、新增或修改的领域词汇与 ADR，以及仍未确认但不阻塞的事项，再用 `rovai send --to-user` 请求用户确认共同理解。只有命令返回 `accepted` 后才结束当前响应。

用户明确确认后结束会话；旧轮或迟到建议不能重开会话。发送异常时遵循 CLI 返回的 recovery 指示，不自行更换请求或盲目重复发送。
