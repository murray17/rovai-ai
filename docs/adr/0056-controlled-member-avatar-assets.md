# ADR-0056: Controlled Member Avatar References and Application-Managed Local Assets

## Context

`AgentProfile` already contains nullable `avatarRef`, but Core currently treats it as an opaque
string and the desktop does not resolve it into a durable image. v0.14 introduces packaged visual
identities for four built-in companions and lets a user derive both a portrait and compact avatar
from one local image.

Persisting an absolute path would expose local filesystem structure, break after move or restore,
and tempt Renderer code to read arbitrary files. Persisting image bytes, crop fields and multiple
rendition columns in `AgentProfile` would mix UI media with identity, concurrency and audit
semantics. Allowing remote/data URLs would add network, tracking and unbounded decode behavior to
an otherwise local-first identity surface.

The existing four companions are also seeded durable Profiles on every database open. Treating the
same names and handles as ordinary create presets would collide with the unique handle constraint.
Adding avatar values only to the seed insert would update new databases but not existing rows;
forcing an unconditional update would overwrite user-selected images.

Finally, a filesystem asset and a SQLite Profile reference cannot be atomically committed or
garbage-collected across Electron Main and Core. The protocol must choose an honest failure and
retention model rather than imply cross-process transactional deletion.

## Decision

### One controlled reference on AgentProfile

`AgentProfile.avatarRef: string | null` remains the only domain field. New values use the Rovai
namespace and exactly one of these forms:

```text
rovai://member-avatar/builtin/{role}/v1
rovai://member-avatar/managed/{assetId}
```

The built-in role is a closed versioned identifier; v0.14 contains
`luoke | muwa | mianzhi | qilu`. A managed `assetId` is a canonical lowercase UUID generated by
Electron Main. References have no query, fragment, credentials or encoded path separators.

Core owns reference validity for Profile writes:

- create and avatar-changing updates accept only `null` or a currently supported controlled
  reference;
- an existing unknown legacy value may pass through an update only when byte-for-byte unchanged,
  so unrelated Profile edits are not blocked;
- a client cannot create or change to an unknown, legacy, absolute, `file:`, remote or `data:`
  value.

Core returns stored legacy values without interpretation. Renderer treats every unknown or failed
reference as a fallback; it never interprets one as a filesystem or network location.

### Split reference, byte and presentation authority

Core/SQLite owns which reference belongs to a Profile, including version checks and handle
uniqueness. The application bundle owns versioned built-in bytes, resolved by a static Renderer
registry. Electron Main owns managed image bytes under the selected Rovai-ai `userData`.
Sandboxed Renderer owns crop interaction, local normalization and session Blob URLs.

Renderer remains `nodeIntegration: false`, `contextIsolation: true` and sandboxed. Main exposes
only closed avatar operations: select one user-chosen source, atomically save one validated
compound asset, and read one fixed rendition from one controlled reference. It does not return an
absolute path or accept a target directory/file name.

Each managed asset is immutable after publication:

```text
member-avatars/{assetId}/
  source.png
  icon-192.png
  manifest.json
```

An edit creates a new asset and updates `avatarRef`; it does not mutate files behind the old
reference. Manifest v1 records fixed filenames, dimensions, byte lengths, SHA-256 digests and the
normalized crop. Main constructs paths only after full reference parsing and independently verifies
bounded inputs and stored integrity.

The avatar store is not the Core MessageAttachment/ManagedBlob domain. Avatar bytes are
application-local presentation media with a compound rendition manifest and do not enter Agent
context, Camp messages, Memory, evidence, audit or Core JSON transport.

### Asset-first commit and orphan retention

Create, replace and remove use this order:

```text
save new managed asset atomically
→ submit agents.create / agents.update
→ make the new reference visible only if Core applies the command
```

The previous asset is never deleted before Profile success. If Core rejects the command or the app
crashes after asset publication, the new asset remains an orphan. v0.14 does not automatically
delete any final managed asset.

A reference scan in Core followed by a Main filesystem delete is not considered proof of
unreferenced state because another Profile update can race between those operations. Future garbage
collection requires a separate protocol with exclusive ownership or an explicit user-directed
cleanup boundary. Strictly named stale temporary directories that can never be referenced may be
cleaned after the single-instance and age checks defined by the version design.

### Existing built-in companions and upgrade

The fixed IDs `agent-luoke`, `agent-muwa`, `agent-mianzhi` and `agent-qilu` remain the canonical
built-in companions. A data migration, despite adding no column, assigns their corresponding
built-in reference only when `avatar_ref IS NULL`. It does not match by mutable handle/name, replace
a non-null value, restore archived state or alter role, Runtime, Capability, Camp or Lead facts.
New database seeds write the same references.

The UI may offer their appearance and suggested identity text as reusable create presets, but a
new Profile receives an independent unique handle. `avatarRef` is presentation only: no role,
persona, motto, trait, Capability, Runtime choice, permission or lifecycle fact is derived from it
after creation.

### Local-only image safety

Only explicitly selected static PNG/JPEG input is in scope. Every boundary has independent file,
byte, decoded-dimension, pixel-area, normalized-output and IPC limits. General image decode occurs
in the sandboxed Renderer; Main performs bounded type/header/structure checks, fixed-path atomic
storage and integrity verification. SVG, animated/underspecified formats, remote URLs and data URLs
are rejected.

Image bodies, original absolute paths and embedded metadata do not enter SQLite, event logs,
audit, diagnostics or exports. Normalization re-encodes the source, strips metadata and derives the
compact rendition locally. Missing, corrupt or externally omitted files degrade to a neutral
fallback and repair affordance rather than preventing database use.

### Backup boundary

The SQLite reference and managed image files are separate local state within the same selected
Rovai-ai `userData`. A complete external backup must preserve that whole directory. Copying only
SQLite is not represented as a complete avatar backup. v0.14 adds no cloud sync or standalone avatar
export guarantee.

## Consequences

- Profile identity, image bytes and rendering each have one explicit owner without exposing
  arbitrary paths to Renderer.
- New installs and upgrades converge while preserving user-edited and archived Profiles.
- Closed references are portable within a complete `userData` backup and cannot initiate network
  loads.
- Asset-first writes prevent a committed Profile from pointing to a not-yet-published new asset
  during normal operation.
- Failed Profile writes can consume disk as retained orphans; v0.14 accepts bounded local leakage
  instead of unsafe deletion.
- Legacy opaque values remain readable and editable in place but cannot multiply through new
  writes.
- Adding a built-in role/version, a new media format, automatic GC or cross-device transport
  requires an explicit contract and corresponding upgrade/acceptance evidence.

## Rejected Alternatives

- Store absolute paths or `file://` URLs: non-portable, path-revealing and unsafe for Renderer.
- Store base64 image bytes or crop/rendition columns on `AgentProfile`: bloats SQLite and mixes
  presentation media with domain concurrency.
- Allow arbitrary or remote URLs: introduces tracking, network policy, cache and decode risks.
- Treat a URI prefix regex as validation: accepts malformed IDs, extra syntax and path confusion.
- Derive live role or traits from `avatarRef`: makes an appearance choice a hidden domain type.
- Unconditionally backfill built-in avatars: overwrites user choices.
- Rely only on the seed insert: leaves upgraded databases without built-in images.
- Delete an old asset after a non-transactional reference scan: races with concurrent Profile
  writes and archived identities.
- Put compound avatar assets through Core JSON or MessageAttachment: changes an unrelated domain
  protocol and sends large UI media through the Core transport without solving rendition UX.
- Support WebP by taking an arbitrary first frame: leaves animation and decoder behavior
  underspecified.
