# 记忆、上下文、文档与队员成长治理愿景

本文记录四项渐进建设方向及已明确的范围边界，作为后续逐项讨论和实施的输入。它不改变当前
Architecture、Contract、开发规范或版本范围，也不代表模型上下文改动方案已经取得二次确认。
当前版本始终从[版本索引](../versions/README.md)的唯一权威指针读取。

## 目标与共同原则

基于现有架构，通过有限改动形成可演示、可解释设计取舍、可追溯实现与验证依据的工程能力。
优先复用现有功能、数据、接口和 Skills，只补必要缺口。每项都应能回答：解决什么问题、如何实现、
如何验证以及适用边界在哪里。

- 提报与二次确认等交互由 Skill 引导，不新增审批系统、独立工作台或练习任务。
- 评测由开发与运行设施完成，不要求产品用户参与评测。
- 运行结果必须来自实际执行；未运行、证据不足、运行受阻分别如实记录，不算通过。
- 设计文档、合同测试通过和用户批准只证明各自覆盖的事实，不能当作实际效果提升。
- 不建设全自动自进化平台。队员成长是经验驱动、用户确认后的行为配置更新，不是模型训练。
- 每项交付包含代码、必要测试与简短说明：问题、复用点、关键取舍、演示步骤、验证事实和剩余限制。

## 1. 记忆治理与基础统计

### 复用基础与目标

沿用 Hearth、Companion、Relationship 三种记忆及现有记忆治理 Skill，继续负责长期经验沉淀、修订、
去重、适用范围判断和权限边界。入口见[在线记忆捕获架构](../architecture/online-memory-capture.md)与
[Memory Capture v3](../contracts/memory-capture-v3.md)。

只补两个观察指标，不做自动召回优化、关键词优化、重排或自动删除：

| 指标 | 计入 | 排除 |
| --- | --- | --- |
| 正文读取次数 | 一次逻辑 `memory.read` 成功返回该条当前正文 | 索引曝光、搜索、`memory.view`、失败、运输重试与重复回放 |
| 修订次数 | 成功产生正式修订 | 初次创建、无变化、失败、待审核候选与重复回放 |

`memory.view` 虽然返回精确 Scope 的完整有效正文集合，但属于治理查重入口，不纳入本指标。
读取频次只能作为关注候选记忆的线索，不代表记忆被正确使用、真正有效或已经改善任务结果。

优先复用现有访问证据和正式 Revision 历史。统计经既有用户入口及受授权的 Agent 查询入口提供；
Skill 沿用调用队员的权限，不获得新的跨 Scope 访问权。历史证据不足以准确去重时，明确计数的
起算范围或不可用状态，不回填虚假的精确累计值。

### 演示与验证方向

演示成功读取与正式修订后的计数变化，并对照搜索、View、无变化修订、待审核、失败及回放不计数。
测试覆盖计数的成功边界、逻辑调用去重、正式发布边界和查询授权；真实有效性仍需任务结果证据。

## 2. 上下文治理 Gate 与每日评测

### 上下文改动方案

复用[核心模型上下文变更治理](../development/model-context-change-governance.md)。目标覆盖模型可见
内容、上下文选择与截断、工具输出、共享 Skill 注入等机制变更；相对现有规则需要扩展的触发范围，
在实施前单独讨论并同步其当前权威，不通过本文直接生效。

修改机制前先生成完整、可审阅的上下文改动方案，至少包含：

1. 精确前后差异和保持不变的权限、语义、选择及证据边界；
2. 方案 revision、受影响的合同与上下文版本，以及兼容、迁移和恢复策略；
3. 待评测代码版本、评测范围、固定比较条件与预先确定的通过标准；
4. 允许的修正轮数、运行预算和停止条件；
5. 开发者审阅后的明确二次确认，绑定具体方案 revision。

Skill 引导确认流程。原始需求或同意讨论不替代对完整方案的二次确认。方案语义变化时更新 revision
并重新确认；实施和报告都必须能对应实际代码与方案版本。

### PR 前验证

复用现有合同测试、Qualification Runner、Benchmark 协议及结果证据。PR 前运行合同测试与新旧版本
对照评测，分别观察最终交付、A2A、记忆与上下文使用、资源及稳定性。

- 固定 Case、输入与初始状态、模型和 Runtime、工具与权限、预算、评分规则等共同条件，明确唯一
  允许变化的上下文因素；各次执行使用隔离状态。
- 保留全部预定样本、原始结果、失败、修正轮次与证据不足，不只展示最佳运行。
- 分别报告通过、退化和证据不足；测试覆盖不到或不可比的维度不能由其他维度补偿。
- 发现退化可以分析和修正，但不得更改评分标准、删除失败样本或无限重跑以取得通过。
- 修正若改变已确认方案的语义，先更新方案并重新确认；新运行保留独立身份并关联旧报告。
- 合同正确性、真实任务表现、语义评审和资源消耗各自报告，避免以调用量或综合分代替质量。

复用入口：[Benchmark 架构](../architecture/benchmark-protocol.md)、
[Benchmark Protocol v3](../contracts/benchmark-protocol-v3.md)、
[Semantic Judge Views v1](../contracts/semantic-judge-views-v1.md)、
[Tool Interaction Measurement v2](../contracts/tool-interaction-measurement-v2.md)与
[Paired Collaboration Experiment v1](../contracts/paired-collaboration-experiment-v1.md)。
现有 Team/Solo 配对协议与上下文新旧版本对照的实验变量不同，不能直接把前者当成后者已实现的证明。

### 每日评测

复用[定时任务](../architecture/scheduled-automation.md)和现有 Runner，在隔离环境运行固定任务集，
保存代码、方案、模型、Runtime、任务集和评分版本，以及计划样本量、实际样本量、结果和趋势。
调度、执行、证据验证和报告分别保留事实；已有调度能力不代表完整每日评测链路已经接通。

缺少数据、机器未运行、依赖不可用或运行受阻时明确标记，不补零、不算通过。模型或环境漂移导致
不可比时保留原值和限制，不直接解释为产品退化。每日运行应有有限预算、超时和重叠处理。

回归集与独立验收保留集分开。日常调试和每日趋势使用回归集，保留集不在每次修正后反复使用；
保留集的运行时机与读取边界在评测方案中预先确定。

### 待讨论与验证

先依据源码和当前合同盘点已有评测能力，再决定最小补充范围。需明确新旧对照的实验定义、上下文
专项 Case、报告如何绑定代码与方案、每日触发链路，以及样本不足时的结论规则。首次真实运行前
所有质量、稳定性和资源收益均为未验证。

## 3. 项目文档结构与治理规范

以目录结构、README 索引和现有文档治理流程及可复用 Skill 为主，不新增重型自动化。
现有入口是[文档导航](../README.md)、[版本索引](../versions/README.md)与
[版本决策治理](../decisions/README.md)。

- 目录明确表达职责和生命周期，区分当前规范、当前版本及历史记录；当前版本保持唯一权威指针。
- 每个治理目录的 README 只说明内容范围、当前入口及新增、修订、归档规则，不复制正文。
- Skill 指导开发者先读当前权威，再修改对应内容、同步索引并运行现有检查。
- 代码与文档不一致时先判断哪方有误，不能修改文档迁就代码缺陷。
- 历史记录不静默重写；勘误和新决定按现有规则留下可追溯记录。
- 涉及模型上下文语义的机制变更接入第二项 Gate。

演示从一个开发任务找到唯一当前入口、同步一次规范与索引修订并运行通用文档检查。
检查通过只证明所覆盖的结构和追溯约束，不能证明所有文档语义正确或与代码完全一致。

## 4. 队员成长：经验提炼与准则提报

作为现有记忆治理 Skill 的一部分实施。在正常用户任务的记忆整理环节，结合读取频次关注候选，
阅读当前正文并对照目标队员已有行事准则。仅提炼适用范围明确、可复用的做事方式。

临时要求、特定项目事实以及已有准则覆盖的内容不重复提升。高频只影响候选关注，不自动修改准则；
成长主题可以选择，但不是提炼经验的前置条件。

### 提报与生效

Skill 向用户展示：目标队员、来源记忆及版本、修改理由、前后差异、适用范围和完整拟生效准则。
用户看过完整方案并明确二次确认后，才通过现有接口更新。方案变化后重新确认；拒绝或未回应时
不修改，也不反复提报同一候选。具体候选标识、来源追溯和重复提报判断优先复用现有记录，实施前
核对是否足以表达这些边界。

沿用现有记录保留修改依据与前后版本，支持撤回。用户批准只说明接受这次配置更新，不证明能力
提升。日常个性化准则更新走 Skill 确认流程，不额外要求用户参与评测；准则生成或注入机制的改变
仍进入第二项 Gate。

### 演示与验证方向

用正常任务中形成的真实经验演示候选读取、已有准则对照、完整提报、确认后更新及撤回。
验证未确认不修改、方案变化需重新确认、拒绝后不重复提报、授权与版本冲突，以及依据和前后版本
可追溯。对行为效果的判断仍需独立任务证据，不能由这些流程测试代替。

## 讨论与交付顺序

- 已确认：记忆治理主体复用现有实现，第一项两个计数延后到第四项一起处理。
- 当前先讨论第二项的评测充分性和最小补充范围；尚未选定具体实现方案、样本量或运行预算。
- 第三项先核对既有目录、索引与治理能力，具体增量另行讨论。
- 本文不分配发布版本，不宣称四项已经实现，不作为执行模型上下文变更的确认凭据。

每项实施收口时，在真正归属的版本记录中追加问题、复用点、取舍、演示、实际验证和限制，并引用
对应代码与结果。本文只维护建设方向、约束和讨论结论，不承接运行证据或复制当前规范。
