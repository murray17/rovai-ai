# Lumen AI 前端设计规范

> 状态：v0.01 Coding Agent 实施规范
> 适用范围：`apps/desktop/src/renderer/**`

## 设计方向

Lumen 采用 **Calm Native Workbench（冷静、原生的工作台）**：保留本地、温暖、长期陪伴的品牌气质，同时让任务工作区保持专业、克制、高信息密度。

- 温暖感来自暖中性色、少量品牌色、角色身份和空状态。
- 对话、命令、审批、Diff、审计和恢复状态以操作清晰度为第一优先级。
- 首页、引导和空状态可以使用衬线标题与灯笼/营地意象；核心工作区不得被装饰性视觉干扰。
- 不采用通用 AI 紫蓝渐变、玻璃拟态、大面积发光或“所有内容都是悬浮卡片”的风格。

## 不可破坏的原则

1. **品牌色、角色色和语义状态色必须分离。**
2. **状态不能只靠颜色表达。** 同时使用文字、图标或形状，并放在稳定位置。
3. **证据优先于氛围。** 命令、路径、审批范围、Diff 和审计元数据必须易读、可扫描。
4. **紧凑但不拥挤。** 可以提高信息密度，但不得牺牲焦点、点击目标和文字可读性。
5. **渐进式修改。** 功能改动不得顺手重做无关页面；优先复用已有组件和 token。

## 信息架构

保持稳定的桌面三层结构：

- 左侧栏：项目、任务和一级导航。
- 中央区域：任务目标、用户/Agent 对话和系统边界事件。
- 右侧检查器：活动、变更、审批和审计。

任务工作区必须让用户快速回答：

- Agent 现在在做什么？
- 哪一步需要我处理？
- 哪些文件发生了变化？
- 当前结果、风险和恢复状态是什么？

默认窗口按 `1440×920` 设计，并必须在应用最小尺寸 `1040×700` 下可用。空间不足时可以隐藏次要元数据或收起检查器，不得隐藏当前状态、审批入口或核心操作。

## 视觉系统

### 颜色

- 优先复用 `styles.css` 中已有的 `:root` CSS Variables；新增共享颜色时先定义 token，不在组件中散落新的十六进制值。
- 暖白、纸张色和低饱和绿色是基础品牌材料，不代表成功状态。
- `success`、`attention/warning`、`danger`、`info`、`neutral/paused` 使用独立语义 token。
- 洛可、沐瓦、眠枝、绮露的角色色只用于头像、身份标记和所有权提示，不得表示成功、警告、危险、选中或禁用。
- 危险操作始终使用危险语义；等待审批和恢复状态不得借用角色色。
- v0.01 只要求完整的亮色主题。未经明确任务要求，不实现暗色模式。

### 字体

- 工作区正文使用 macOS 系统无衬线字体栈。
- 命令、路径、日志、哈希和 Diff 使用等宽字体。
- 衬线字体只用于首页、欢迎页、空状态或品牌级标题。
- Tabs、表单、审批、活动、审计、Diff 和正文不得使用衬线字体。
- 正文通常为 `13–14px`，等宽内容通常为 `12px`；不得为追求密度继续缩小关键内容。

### 间距和表面

- 使用 `4 / 8 / 12 / 16 / 20 / 24 / 32px` 间距尺度。
- 核心工作区优先使用分隔线、背景层级和选中态分组，少用独立浮层卡片。
- 常规控件和面板圆角保持在 `6–10px`；核心工作区不得使用超过 `12px` 的夸张圆角。
- 阴影只用于 Dialog、Popover、菜单、Command Palette 等真正浮在内容之上的元素。
- 动画以 `120–200ms` 的透明度或小位移过渡为主，不使用循环脉冲、光晕或大幅弹簧动画。

## 项目专属界面模式

### 对话与系统事件

- 用户消息、Agent 消息、系统事件、错误和恢复边界必须有不同的行类型。
- Agent 消息展示角色身份，但角色色只能点缀头像或细边，不填满整块消息。
- 系统事件保持中性、紧凑、带时间戳，不得伪装成 Agent 发言。
- “正在工作”必须尽量伴随最近活动证据，避免只有无期限的 `Thinking…`。

### 活动与命令

- 每次命令执行作为一个原子活动块展示，不把多个命令输出混成无结构日志。
- 可用数据存在时，活动块应显示命令、cwd、状态、时长、退出码和可展开输出。
- 文件变更、命令执行和 Runtime 状态应能从图标、标题和状态文字直接区分。

### 审批

- 审批是阻塞性的安全决策，不得混在普通聊天气泡中。
- 审批界面必须说明请求能力、准确范围、请求原因、允许/拒绝的后果和当前阻塞影响。
- 危险或不可逆决策的默认焦点应放在最安全的选项。
- `Approve` 与 `Reject` 不得只靠左右位置或颜色区分。

### Diff 与审计

- Diff 使用等宽字体；新增/删除行同时使用符号和语义底色。
- 文件路径、变更类型和折叠状态必须明确；装饰图形不得进入 Diff 区域。
- 审计记录不是聊天，应优先展示时间、Actor、动作、目标、结果和证据。
- 长路径、命令和 JSON 必须支持换行、滚动或展开，不得撑破布局。

### 恢复与错误

- `recovering` 是持久的一等状态，不是短暂 Toast。
- 恢复界面应说明正在恢复什么、最后已知状态、是否需要用户操作以及成功/失败结果。
- 错误必须说明发生了什么、影响是什么、能否重试，以及是否保留了部分数据。

## 组件与交互

- 优先使用现有 Radix Dialog 和 Tabs；没有明确理由不得新增 UI 框架。
- 所有交互控件必须具备 `default / hover / pressed / focus-visible / disabled`；异步控件还需要 `loading`。
- Tabs 内容需要异步加载或渲染成本较高时使用手动激活。
- Modal 必须包含可访问名称和描述、锁定背景交互、支持 `Escape`，关闭后把焦点返回触发元素。
- 表单使用可见 Label；Placeholder 不能代替 Label。
- 重要运行状态和审批变化应使用适当的 `aria-live`，但避免为流式日志逐字播报。
- 主要操作必须可用键盘完成，并与可见布局顺序保持一致的焦点顺序。
- 可点击目标至少 `28×28px`；不得通过隐藏焦点环换取“干净”视觉。

## 无障碍

- 以 WCAG 2.2 AA 为最低目标。
- 普通文本对比度至少 `4.5:1`；组件边界和状态指示至少 `3:1`。
- `focus-visible` 必须清晰，且不得被 `overflow`、Sticky Header 或 Overlay 遮挡。
- 优先使用语义 HTML，只在必要时补充 ARIA。
- 支持 `prefers-reduced-motion`；减少动态效果时不得丢失状态反馈。
- Icon-only 控件必须有可访问名称。

## Coding Agent 实施规则

- 修改 UI 前先阅读现有 `App.tsx`、`styles.css` 和相关测试，沿用已有交互模型。
- 新增样式优先复用 token 和现有 class；只在出现重复模式时抽取共享组件。
- 不为单个功能引入新的字体、图标库、CSS 框架或状态管理库。
- 纯事件投影、状态映射和格式化逻辑应保持为可测试的纯函数。
- UI 变化必须覆盖相关的 loading、empty、error、disabled 和恢复/审批状态，不能只实现理想路径。
- 视觉改动应同时检查 `1440×920` 和 `1040×700`；环境允许时提供前后截图。

## 完成检查

前端改动完成前确认：

- [ ] 品牌色、角色色和语义色没有混用。
- [ ] 关键状态不只依赖颜色。
- [ ] 键盘和 `focus-visible` 可用。
- [ ] 审批说明了范围、原因和后果。
- [ ] 命令、路径、日志与 Diff 仍然清晰可读。
- [ ] loading、empty、error、disabled 等相关状态完整。
- [ ] 最小窗口尺寸下没有遮挡核心操作。
- [ ] 运行了与改动相关的 typecheck、测试和构建验证。
