# DSH 模型配置不可见、思考档位错配与加载结果被覆盖

> **爱丽丝的小结：** DSH 这一轮不是一个“模型列表没刷新”的单点故障，而是配置来源、模型能力归属、缓存和异步发布几个边界接连暴露了问题。
> 修复始终保留原生 ACP 主路径：配置让 DSH 解释，能力按目标模型读取，旧结果不能覆盖新结果。
> Windows 路径归一和下拉框迟到响应是两处独立修复，不能因为前者已合入，就把后者也算作解决。

## 摘要

用户最初反馈 DSH 拉取模型困难、配置了多个中转站后执行仍排队，随后在本机配置复用和实际选模中逐步暴露出：
Web 配置的模型不出现在 ACP 目录、`sub2api / gpt-6.1-sol` 被设置了不支持的 `max`、空缓存无法恢复读取，
以及加载中展开推理强度菜单后，加载结束却没有保留新档位。

这一系列问题不能统一归因于 DSH 升级、沙箱或某个模型。已确认缺陷分布在四层：
**原生配置与 Web 补充、目标模型能力、缓存读取与合并、跨请求结果发布。** Windows 还存在同一程序不同路径写法造成的指纹不一致。

相关修复经 PR #679、#681、#683、#684、#685、#686 合入 main，并纳入 `v0.4.7` 代码及
[发布说明](../../build/release-notes.md)。最低支持版本仍为 `0.1.5-rc.2`；没有要求用户先打开 Web，
没有新增配置数据库、迁移系统或每次业务执行的双重探测。

## 影响与证据边界

| 用户可见现象 | 已确认的对应缺陷 |
| --- | --- |
| Web 已配置模型，Rovai 目录却看不到 | Profile 配置不自动等同于 ACP 的有效模型配置，缺少受控补充 |
| Web 补充失败，原本可用的原生模型也被拒绝 | 拒绝名单与局部原生 Provider 集合被误当成全部路由的权威 |
| 修改 Web 无关设置后，执行提示配置过期 | Host 指纹与显式选模时的全文件校验口径不一致 |
| 目标模型报 `unknown reasoning effort ... max` | 把初始 ACP 模型的档位及默认值扩散给其他模型 |
| 空缓存反复失败，点重试也不真正读取 | 缓存结果的严格发布校验在实际读取前抛错 |
| Windows 检查／刷新结果无法确认 | 普通路径与长路径前缀进入同一指纹的方式不一致 |
| 推理强度加载结束后新档位丢失 | 较早发出的模型目录响应迟到，覆盖更新的目标能力 |

最初“全部排队”的用户反馈没有一份覆盖所有队员的完整因果追踪；不能据此宣称每次排队都由以上某一个缺陷造成。
用户报告的修复耗时和额度消耗反映了真实使用成本，但没有按缺陷拆分的计量，不在本文估算统一损失。
配置迁移污染是设计审查与隔离验证发现的风险，本文不把它写成已经确认发生于用户日常配置的数据损失。

本复盘核对截至 `2ab444469` 的代码、固定修复提交、PR 与版本验证记录；本次写作不重新运行 DSH 或付费模型。
早期 macOS 验收、后续 Windows 协议验收和 Windows 浏览器交互验收分别标明，不能互相替代。

## 根因与修复

### 1. 配置来源发生变化，原生 ACP 与 Web 不能直接等同

旧共享配置和新版 Profile 配置的实际有效范围不同。固定版本 `dsh-v0.2.1-alpha.1` 的原生组合顺序包含
Bundle、Profile、Home Patch、命令行 Patch；插件行的 `config` 是整块替换，导出的表达式也尚未求值。
因此，简单在 ACP 启动参数后追加 Web Patch，既不能可靠保留原生配置，也可能让临时覆盖进入 DSH 自己的旧配置迁移。
[DSH 固定版本 CLI 说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-alpha.1/apps/cli/reference/README.md)

修复将 Provider 准备集中到 [models.mjs](../../crates/rovai-core/src/dsh/models.mjs)，由探测和实际 Host 共同使用。
DSH 完成原生初始化／需要的原生迁移后，Rovai 才准备完整的 Web 补充和既有 Responses 兼容参数，并应用到内存配置。
最终模型目录仍来自原生 ACP，不由 Rovai 从 YAML 另造一份目录。

冲突以 Provider 为边界：保留原生明确用户配置与显式禁用，允许 Web 明确配置补充内置默认；
同名 Provider 不拼接端点、密钥和模型数组，表达式与凭据仍交给 DSH 解析。迁移归 DSH，Rovai 只隔离自己的临时模型覆盖。
实现与原生迁移、删除后不残留的验收见 [PR #679](https://github.com/murray17/rovai-ai/pull/679)。

### 2. 补充配置的失败边界扩大，误伤原生能力

初版准备逻辑先处理同名 Web Provider 的解析失败，再判断原生配置优先；结果是原生 Provider 虽未被覆盖，
却已进入拒绝名单。Web 整体不可用时，另一个校验把模块能识别的 `nativeProviders` 当作所有原生路由集合，
误拒其他插件提供的模型。

`4f5b4cafa` 先保留原生有效用户配置，再处理 Web；拒绝只针对实际依赖失败补充的选择。
目录和保存／冻结选择沿用原生 Provider＋Model 身份，并携带最小 `dshSource` 信息。
选了 Web 路由而补充失效时，即使原生存在同 ID，也在提交正文前明确拒绝，不能借“恢复可用”悄悄换中转站。

同时移除显式选模阶段重复的全文件新鲜度检查：保留等待准备完成和路由验证，把输入变化检查留在准备与目录发布边界，
后续 Run 通过已有 Host 兼容性入口判断。这样 Web 主题等非模型变化不会与已有指纹口径冲突。
对应行为见 [dsh.rs](../../crates/rovai-core/src/dsh.rs) 和 [PR #679](https://github.com/murray17/rovai-ai/pull/679)。

### 3. 思考强度被错误当作整个 Runtime 的公共能力

一次 `session/new` 返回的 `reasoning_effort` 属于当时选中的模型，旧逻辑却把它复制给目录中所有模型，
还可能在用户未指定时把目录默认值填进冻结配置。初始模型支持 `max`，并不意味着 `sub2api / gpt-6.1-sol` 也支持它。

`0071717e1` 改为按需在非业务 ACP Session 中选择目标模型、读取更新的选项。
执行时先核验身份和来源，再选目标模型、读取其最新 `configOptions`、校验显式强度，最后提交正文。
没有保存 `reasoning_effort` 就保持缺省；“模型默认”不是 `off`，也不是固定的 `high`。
显式保存不支持的 `max` 会在正文前报错，不自动降级，不重建 Session 绕过，也不批量删除历史选择。
[PR #681](https://github.com/murray17/rovai-ai/pull/681)

### 4. 缓存需要累计能力，未命中不能当成模型不存在

`235ad032f` 在现有 SQLite 模型目录中累计逐模型能力，记录安装／环境、配置上下文、来源、成功时间和确认状态。
同一上下文中读取 B 不清掉 A，也不刷新 A 的成功时间；确认无档位同样缓存。
60 秒是访问时判断的新鲜期，不是定时扫描所有模型。配置变化立即失效确认；失败保留历史和成功时间。
[PR #683](https://github.com/murray17/rovai-ai/pull/683)

后续审查发现另一个控制流错误：前端先读 `cacheOnly`，随即严格发布；缓存中根本没有目标模型时就抛错，
后面的真实读取永远到不了，重试仍走同一条失败路径。
`da189dbbb` 将缓存的可选展示与实际结果的严格验证分开：缓存缺项继续查询，实际读取后仍缺目标才报错，身份核对保持。
`15ef0422e` 增加 240 ms 后显示的控件内加载指示，缓存命中不闪烁，默认选项和保存保持可用。
这个加载状态只针对 DSH 的思考档位读取。[PR #684](https://github.com/murray17/rovai-ai/pull/684)

### 5. Windows 同一程序的两种路径写法，造成假配置变化

探测中的规范路径可能为 `\\?\C:\…`，目录提交使用 `C:\…`。旧 `model_options_context()` 把调用处传入的路径
直接纳入上下文，两种写法会得到不同指纹，成功的探测结果随后被当成 `superseded`／`deferred` 丢弃。

`42ba5a077` 在共同入口先做 `canonicalize()`，再复用 `runtime_visible_path()`，使命令环境、文件身份和摘要使用同一路径。
真正的程序内容、配置或环境变化仍会使缓存失效；没有放宽结果发布门禁。
[PR #685](https://github.com/murray17/rovai-ai/pull/685)

### 6. 较早请求最后返回，覆盖已经读到的新档位

用户补充的场景是 Windows 上 DeepSeek v4.1，加载中点击推理强度后，转圈停止、列表没有正常更新。
最初 macOS 夹具只验证“保持菜单展开 → 能力返回”，这个顺序能够通过，**但没有覆盖另一路旧目录最后返回**。

后续 Windows 定向复现确认以下竞态：

```text
普通模型目录请求 A 发出，持有旧观测
    → 目标模型能力请求 B 完成，菜单已经显示新档位
    → A 迟到，直接 setLive() 覆盖 B
    → 加载状态已结束，档位却退回旧列表／尚未核对
```

`6e167d4a2` 将两条返回路径收敛到同一 `updateCatalog()`，在安装身份一致时比较目录观测时间，
保留更新的结果。已打开的 Radix 菜单原位更新，无需重开；已有保存值不因后台返回改变。
这是一处 Renderer 发布顺序缺陷，独立于 Windows 路径指纹错误。
[PR #686](https://github.com/murray17/rovai-ai/pull/686)

## 为什么问题分多轮暴露

1. **一次成功覆盖不了来源变化。** 共享设置、Profile、自定义 Provider、其他插件和内置默认具有不同语义，早期通路没有完整覆盖冲突与失败隔离。
2. **能力的归属粒度错误。** 把当前 Session 的模型能力当成 Runtime 公共能力，使目录、草稿和执行同时继承错误的 `max`。
3. **防过期检查口径不一致。** 同一执行先接受模型摘要，后又被无关文件变化拒绝；有效性需要在已有统一入口判断。
4. **测试缺少关键缺项与乱序。** “目标存在但没读取”没有覆盖“目标缓存条目不存在”；“能力返回更新菜单”没有覆盖“另一请求随后覆盖它”。
5. **平台差异没有进入最初身份样本。** macOS 结果无法证明 Windows 路径等价；后来 Windows 的协议修复也不能代替 Renderer 交互验证。

这些是边界和验证样本的缺口，不归咎于某位执行者。用户持续反馈帮助我们把验收从“能列出／能启动”推进到
“来源正确、默认正确、请求正确，且打开的菜单最终保持正确”。
