# Windows Codex Runtime Discovery and Acceptance Isolation Gaps

## Executive summary

On 2026-08-25 and 2026-08-26, release-candidate validation on a real Windows x64 host exposed two
classes of gaps around Codex Runtime discovery. First, the existing product model reused the
Desktop process's inherited `PATH` and admitted only native `.exe` files. It therefore could not
reliably discover an official Codex installation added after Rovai started, or the `codex.cmd`
entrypoint created by npm/pnpm. The first safe npm implementation also recognized the previously
observed npm shim template but not the different, valid template generated by npm 11.17.0, so its
exact-template parser correctly failed closed and the UI continued to show Codex as Missing.

Second, the local acceptance harness did not initially isolate every source in the product's
discovery precedence. A native binary under Codex's standalone package directory could make the
supposed clean baseline remain available. Later, a pre-existing user-level `ROVAI_CODEX_BIN`
pointed to the temporarily removed official executable. That Adapter override is intentionally a
terminal candidate set, so it correctly suppressed automatic npm/PATH discovery and made a fixed
build appear broken. The harness had preserved the override but had not cleared and restored it as
part of the test boundary.

The product correction now rebuilds an immutable Windows search environment on every rescan from
inherited, HKCU User, HKLM Machine, and known-location paths; admits only the closed
`.exe/.cmd/.bat` entrypoint set; and resolves a narrowly verified npm/pnpm Codex locator to its real
native `codex.exe`. The parser accepts both the legacy and npm 11.17.0 exact shim shapes while
retaining package containment, metadata, interpreter, locator-content, and native-target identity
checks. Generic command shims remain explicit managed-process identities rather than being
misrepresented as native executables.

After the acceptance harness also isolated the standalone binary and `ROVAI_CODEX_BIN`, the running
packaged Rovai build reached a genuine Missing baseline. npm 11.17.0 then installed
`@openai/codex` 0.149.1, and clicking Rescan without restarting Rovai resolved the platform package's
native Windows executable, reported `codex-cli 0.149.1`, and reached `ready`. The original official
and standalone 0.148.0 installations and the user's original override were restored; the temporary
npm installation was removed. The fix merged through
[PR #64](https://github.com/murray17/rovai-ai/pull/64).

This was a release-blocking local validation incident and near miss, not a production outage. No
Codex authentication/configuration data, Rovai database data, or user work was deleted. The review
is blameless: the failure came from incomplete cross-platform discovery and acceptance invariants,
not from user actions, npm, or the valid fail-closed override behavior.

## Impact

The immediate impact was delayed Windows release validation and contradictory acceptance results.
The operator could not trust that a visible Missing or Available state represented the intended
candidate source. A restart sometimes appeared to change the result because a new process inherited
the updated User PATH, but restart was not an acceptable substitute for the required Rescan
semantics.

Before the fix, Windows users with an already-running Rovai instance could fail to discover a fresh
official Codex installation. Users whose package manager exposed Codex through `codex.cmd` could
also remain Missing even though a new terminal resolved the command. During the final acceptance,
the product fix itself was temporarily masked by an old explicit override; this affected the test
conclusion rather than adding a product fallback requirement, because explicit override failure is
supposed to remain terminal.

There was no evidence of a production/customer outage or unauthorized process launch. The parser
rejected the newly observed npm shape instead of executing or guessing through it. No Camp,
Conversation, AgentRun, Runtime binding, Codex Home, authentication file, or user configuration was
removed to recover. The acceptance workflow used recoverable backups for executable sources and
restored the pre-test installation state.

## Detection and response

The incident was detected through a real-host sequence rather than a unit test: prepare a Missing
baseline, install from the official channel, rescan the running App, restore Missing, install through
npm, and rescan again. The first preparation run also encountered unrelated `codex.exe` processes
owned by Codex Desktop; the harness was narrowed so process names alone did not define a Rovai
Runtime candidate.

When the npm installation completed but Rescan still showed Missing, the generated `codex.cmd` was
compared with the exact templates in Core. npm 11.17.0 placed its `PATHEXT` update within the
conditional branch and emitted a different final line than the legacy template. The target package,
metadata, and native executable were otherwise valid. A second exact template was added rather than
loosening parsing or executing the script.

After rebuilding and installing that change, another Missing result was traced through the full
candidate precedence. The user-level `ROVAI_CODEX_BIN` still selected the old official path. Clearing
that variable for the acceptance boundary, while snapshotting it for restoration, allowed automatic
npm discovery to run. The already-running App then succeeded on Rescan, proving that a Rovai restart
was not required.

The response kept `%USERPROFILE%\.codex` outside the isolation boundary, moved only known executable
sources to recoverable backups, recorded the selected shim and native target, and restored the
original official installation, standalone package, and environment override after verification.

## Technical root cause

The product and acceptance failures had related but distinct systemic causes.

### Product discovery model was not Windows-complete

The previous search environment was effectively frozen when Desktop started:

```text
Desktop inherited PATH
  -> search native executable names only
  -> cache discovery result
```

The official Windows installer updates User PATH for future processes. It does not retroactively
change the environment inherited by an already-running Rovai process. npm and pnpm normally expose
the package through `codex.cmd`, not a sibling top-level `codex.exe`. Consequently, the earlier model
could miss both supported installation paths for different reasons.

The systemic product root cause was treating executable discovery as a mostly Unix-shaped PATH
lookup instead of a host-specific, immutable search-environment capture with explicit Windows
entrypoint identities. Merely adding PATHEXT behavior would have made discovery broader without
preserving the executable, interpreter, argv, and process-ownership guarantees required at launch.

The initial secure npm implementation deliberately allowed only exact known shim bytes and validated
package containment and metadata before resolving a native target. Its fixture represented the
legacy npm template. npm 11.17.0 generated a second valid template with different control-flow
placement for `PATHEXT`. Because the compatibility set was incomplete, the parser classified the
shim as unverified and failed closed. This was a coverage gap, not a reason to weaken validation.

### Acceptance did not isolate the same precedence model

The intended acceptance state was:

```text
explicit/manual source absent
Adapter override absent
official and standalone sources absent
npm/pnpm source absent
PATH/known-location winner absent
  -> Codex Missing
```

The first harness version concentrated on official and package-manager installations. It did not
fully attest the standalone executable source. It also preserved `ROVAI_CODEX_BIN` but left it active
during automatic-discovery tests. Since Adapter overrides are terminal candidate sets, the stale
override correctly prevented fallback to the newly installed npm candidate.

The systemic acceptance root cause was maintaining a separate, incomplete mental model of discovery
precedence instead of deriving the baseline checklist from the product's closed candidate sets. The
harness could therefore report that filesystem preparation had completed while the running product
still had a higher-priority source.

## Contributing factors

### Unit fixtures covered a previous npm generator shape

The parser was tested against an observed npm template, but there was no real package-manager install
gate that compared the currently generated Windows shim with the closed allowlist before packaged-App
acceptance.

### Process names were initially over-broad evidence

Codex Desktop also runs processes named `codex.exe`. Treating any such process as a blocker delayed
preparation even when the process path was unrelated to Rovai's Runtime candidate or the executable
source being moved.

### Explicit override state was easy to overlook

`ROVAI_CODEX_BIN` is durable user environment, while the visible install/uninstall actions were
filesystem and package-manager operations. The variable did not appear in npm's successful output,
but it had higher discovery precedence than that newly installed package.

### The visible state did not explain the winning candidate set

The Settings result showed Missing/Available, but the normal surface did not make it obvious that a
terminal Adapter override had prevented automatic candidates from being considered. Diagnosis
required inspecting environment and structured discovery evidence.

### Restart could accidentally hide the original gap

Restarting Rovai after an installer changed User PATH could make inherited PATH appear correct. That
would mask the requirement that Rescan itself capture current Registry PATH and would not validate
the intended no-restart behavior.

## Why existing safeguards did not prevent the incident

- Existing discovery tests were strong for native executables but did not model the complete Windows
  installer and command-shim ecosystem.
- Exact-template validation failed safely, but the compatibility fixtures were not synchronized with
  the current npm-generated template before real-host acceptance.
- The acceptance script preserved Codex auth/config as intended, but its executable-source allowlist
  was initially narrower than product discovery.
- The harness checked installation paths and package managers without first neutralizing all higher
  precedence explicit sources.
- CI could validate compilation and deterministic fixtures, but it did not install the current npm
  package on a real Windows host and exercise Rescan in an already-running packaged App.
- UI state alone could not distinguish "no automatic candidate" from "automatic candidates were
  suppressed by a failing explicit override."

## What was not the cause

- npm installation was not broken. It installed `@openai/codex` 0.149.1 and its Windows x64 platform
  package successfully.
- The current npm shim was not malicious or malformed. It was a valid generator variant absent from
  the closed compatibility set.
- The terminal behavior of `ROVAI_CODEX_BIN` was not a product bug. Falling back after an explicit
  override fails would silently replace the user's selected installation.
- A Rovai restart was not required after the final fixes and correct acceptance isolation; live Rescan
  found the npm installation.
- Unrelated Codex Desktop processes did not provide the Runtime candidate and did not need to be
  terminated for discovery validation.
- Codex auth/config under `%USERPROFILE%\.codex`, Rovai database contents, and stale UI snapshots did
  not cause the parser mismatch.
- The earlier official-installer download delay did not cause the npm discovery failure.

## Resolution and recovery

The merged change established one Windows-specific discovery and launch chain:

1. Every startup/rescan captures inherited PATH, current HKCU User PATH, current HKLM Machine PATH,
   and known locations into a new immutable search environment without mutating Registry or Core's
   global environment.
2. Candidate extensions are closed to `.exe`, `.cmd`, and `.bat`, with stable precedence and no
   PowerShell/PATHEXT expansion.
3. Known Codex npm/pnpm `codex.cmd` files are read only within a bounded size and matched against exact
   supported templates, including both observed npm variants.
4. Package entrypoint, platform dependency metadata, containment, fixed vendor path, interpreter,
   locator content, and native target identity must all validate before Core binds Installation,
   Probe, and launch to the native `codex.exe`.
5. Other bounded `.cmd/.bat` candidates retain a distinct `windows_command_shim` identity and launch
   only through the Managed Runtime Process serializer and canonical System32 interpreter.
6. Locator or target changes invalidate previous Ready evidence and require a new probe.

The final packaged-App acceptance proved these outcomes on the real Windows host:

```text
prepared sources and override isolated -> Codex Missing
npm 11.17.0 installs @openai/codex 0.149.1
running Rovai: Rescan
  -> npm codex.cmd recognized
  -> @openai/codex-win32-x64 native codex.exe selected
  -> reportedVersion = codex-cli 0.149.1
  -> pathState = valid
  -> availability = ready
```

Recovery restored the pre-test user state rather than retaining the validation setup. The original
official and standalone 0.148.0 executables and `ROVAI_CODEX_BIN` value were restored, the test npm
package was uninstalled, and the recoverable acceptance workspace was sent to the Recycle Bin.

## What went well

- Exact-template validation rejected an unknown script shape without executing it or guessing a
  native child target.
- Testing used a packaged Windows App, a real official installer/npm package, and an already-running
  process rather than relying only on fixtures.
- The final test proved the user-facing requirement directly: Rescan discovered the new installation
  without an App restart.
- Candidate identity evidence retained the npm locator and bound formal execution to the native
  Windows target.
- Acceptance isolation kept Codex auth/config out of scope and used recoverable moves for executable
  sources.
- The original installation and environment state were verified after restoration.
- Linux Clippy caught incorrectly ungated Windows-only helpers before merge, and all five PR checks
  passed after correction.

## What could be improved

- Repository-owned Windows acceptance should enumerate every discovery precedence layer before it
  labels a baseline Missing.
- Current npm/pnpm generator shapes should be exercised by a release-candidate smoke or refreshed
  fixture policy, while exact parsing remains fail closed.
- Runtime diagnostics should state which terminal candidate set won and why lower-precedence
  candidates were not considered, without exposing full user paths or secrets.
- Acceptance evidence should record structured detection, mitigation, validation, restore, App build,
  selected locator, and selected native-target timestamps.
- Process blockers should be tied to the specific executable source/ownership being changed, not only
  to a shared process filename.

## Where we were fortunate

- The defect was found during local release acceptance before the change reached broader Windows
  distribution.
- The unrecognized npm template failed closed. A permissive parser could have executed an arbitrary
  command file while claiming native Codex identity.
- The stale explicit override produced a visible failure instead of silently selecting an unexpected
  fallback installation.
- The host retained both official and npm installation options, making the discovery precedence and
  no-restart behavior reproducible in one session.
- The acceptance workflow had recoverable backups, so the user's original installation and override
  could be restored without reconstructing credentials or configuration.

## Recurrence criteria

This incident is considered to have recurred if any of the following occurs on a supported Windows
host:

- an official Codex install added after Rovai starts is not found by Rescan;
- a supported npm/pnpm Codex shim passes the closed compatibility contract but is not resolved to its
  verified native Windows target;
- an unknown or changed shim is executed, guessed through, or represented as native Codex identity;
- changing locator content or its resolved target does not revoke previous Ready evidence;
- automatic discovery falls back after a manual path or Adapter override fails;
- acceptance labels a baseline Missing without attesting explicit/manual, Adapter override,
  official, standalone, npm/pnpm, Registry PATH, and known-location sources; or
- an acceptance restore leaves installation, environment override, auth, or configuration state
  different from its recorded pre-test state.

## Lessons

Runtime discovery is not only a PATH lookup. On Windows it is a versioned security boundary that
combines process environment, Registry state, file types, script generator shapes, package metadata,
interpreter identity, and native launch ownership. Supporting a package-manager entrypoint safely
means treating the shim as verified locator evidence, not as permission to execute an arbitrary
script or pretend Node is the Runtime.

Acceptance must implement the same precedence model as the product. A clean baseline is an attested
absence across every candidate set, not merely an empty installer directory. Finally, no-restart
Rescan should be tested from an already-running packaged App; restarting first can erase the exact
environmental difference the feature exists to handle.
